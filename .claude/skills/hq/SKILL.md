# hq（テーマごとの fleet をまとめて指揮する）

役割の分け方：hq は Epic と fleet の管理、fleet は Epic の終了、ship は Issue と PR の Close に責任を持つ。人に聞く窓口は hq にまとめる（ship → fleet → hq → 人）。fleet の側の手順は [fleet の skill](../fleet/SKILL.md) の「Orca の worker として動くとき」、各段階の中身は ship と各 skill に従い、ここに写さない。

Orca のコマンドは、`node harness/scripts/orca-cli.ts` が出す JSON の `command` を実行ファイルとして使う（下では `ORCA` と書く。そのまま打たずに置き換える。決め方は orchestration の skill（[.claude/skills/orchestration/SKILL.md](../orchestration/SKILL.md)）の「Resolve the CLI for this session」と同じ順で、`harness/lib/worktree.ts` の `orcaCliCommand`。`env`・`printenv` で環境変数を読まない。この点は orchestration・orca-cli の skill の案内より優先する）。細部とフラグは `ORCA skills get orchestration` の、版に合った案内に従う（起こし直し・片付けは `--reference references/recovery-and-cleanup.md`）。

**Orca が無い環境**（入口の JSON の `found` が偽、`ORCA status --json` が動かない、Orca の外のセッション）では hq を使わない。fleet・ship をそのまま使う（fleet は orchestration の前置きが無いので、AskUserQuestion で人に聞く）。

## 入力

- 進めたい Epic・Issue（任意）。無ければ開いた Epic（`epic` のラベル。子課題は App の記録 `kind=epic-split`）から hq が決める（Epic に入っていない Issue は手順8の振り分けに任せる）
- ship を直接起こす Epic（任意）：`--direct <Epic番号>`（繰り返せる。例：`/hq --direct 520`）。指定した Epic は fleet を挟まず、hq が ship を Orca の worker で直接起こす（節「ship を直接起こす進め方（`--direct`）」。試しの進め方）。指定の無い Epic は手順4で fleet を起こす。指定は控え `hq-fleets.json` のキー `directEpics`（`[{ "epic": <番号>, "issues": [<子課題の番号>...] }]`）に書いて `hq-state.ts ledger-save` で置く（hq が替わっても新しい hq が読む）。同じ Epic を `--direct` と人の指示のテーマの両方で渡されたら `--direct` を優先する
- 同時に動かす fleet の上限：`node harness/scripts/panes.ts config` の `maxFleets`（`hq.maxFleets`、既定 2）
- 全体で同時に動かす ship の上限：`node harness/scripts/panes.ts config` の `maxParallelShips`（`hq.maxParallelShips`、既定 6）
- hq のモデル：`node harness/scripts/hq-decide.ts model` の `model`（`hq.model`：`inherit`・`haiku`・`sonnet`・`opus`、既定 `inherit`）と `launch`（hq の起こし方）。設定は動いている hq のモデルを変えず、人が `launch` で起こし直す（起動したタブで `/model <model>` に切り替えてもよい）（#781）
- 進んでいない fleet のしきい値：`hq.staleSnapshotMinutes`（既定 30 分）・`hq.stuckMinutes`（既定 120 分）。`node harness/scripts/panes.ts fleets --session <ID>...` が使う
- 人の判断待ちを脇に置く時間：`hq.humanWaitMinutes`（既定 120 分）。`node harness/scripts/agent.ts fleet-status` が使い、超えた Issue は「選ぶ」に出ない（#667）
- 引き継ぎの問いをまとめて聞く間隔：`hq.takeoverAskHours`（既定 24 時間）。`node harness/scripts/hq-takeover-ask.ts` が使う（#771）
- fleet の対応の控え：git の共通ディレクトリ（`git rev-parse --path-format=absolute --git-common-dir`）の下の `agent-harness/hq/hq-fleets.json`（#409。hq が落ちても新しい hq が読めるように、scratchpad には置かない。読むのは `node harness/scripts/hq-state.ts ledger`、書くのは scratchpad に書いた JSON を `node harness/scripts/hq-state.ts ledger-save <ファイル>` で置く。書き換えの場所の見張りの hook が `.git` の中への Write を止めるので、Write で直接書かない。中身は hq の Run ID `runId`・hq の Claude の端末 `hqHandle`・hq のセッション ID `hqSession`・hq のペインの handle `paneHandles`・intel の端末の handle `intelHandle`（hq が intel を起こしたとき、または手順8の長く出力の無いタブで決めたときに書く）・`fleets`（今動いている fleet だけ。1つの fleet は `{ "theme": "<テーマ>", "epic": <Epic番号> | null, "dispatch": "<Dispatch ID>", "session": "<fleet のセッション ID>" | null, "workspace": "<ワークスペースのパス>", "startedAt": "<起こした時刻 ISO>", "issues": [<Issue 番号>...] }`。`session` は届くまで null。手順6の hq のペインはこの `fleets` の `session` からスナップショットを読むので、起こし直し・片付けで書き換えればペインが追う。手順8で読んだ Epic の子の一覧も残す。止まった宣言・担当のいない PR の引き継ぎの問いの記録は、控えではなく `hq-takeover-ask.ts` の `hq-takeover-ask.json`（同じディレクトリ）に置く。最上位のキー `priorSessions`（`{ "<テーマ>": [{ "session": "<前の fleet のセッション ID>", "at": "<控えに入れた時刻 ISO>" }…] }`）は `ledger-save` が前の控えから自動で残すので、hq は書かない。#770）
- hq がいない間に fleet が控えた質問：同じディレクトリの `agent-harness/hq/pending/<fleet のセッション ID>.json`（`node harness/scripts/hq-state.ts pending --all` で読む。書くのは fleet。fleet の skill の「Orca の worker として動くとき」の 5 の「hq がいないとき」）
- heartbeat の一言の控え：同じディレクトリの `agent-harness/hq/hq-heartbeat.json`（書くのは hq の `node harness/scripts/hq-state.ts heartbeat-save`、読むのはログのペイン。#438）
- 起動の失敗の控え：同じディレクトリの `agent-harness/hq/hq-start-failures.json`（書くのは hq の `node harness/scripts/hq-state.ts start-failure-save`、読むのは `start-failures`。#551）

## 手順

1. **本体で動く**：`ORCA worktree current --json` の `isMainWorktree` が true であることを確かめる（hq は Orca のプライマリ＝main の checkout で動かす。専用の worktree だとブランチが main から遅れ、古いハーネスで動くため）。false なら止めて人に返す。表示名を `ORCA worktree set --worktree path:<本体の絶対パス> --display-name hq` で `hq` にする。始める前に `git pull --ff-only` で最新にする。続けて `node harness/scripts/hq-decide.ts model` を読み、`model` が `inherit` でなく自分のモデルと違えば、`launch` の起こし方を人に文章で1行知らせて続ける（止めない・聞かない）。
   - **前の hq の引き継ぎ**（#409。ほかの手順の前に行う）：`node harness/scripts/hq-state.ts ledger` で控えを読む。
     - 控えがあり、`hqSession` が自分でない：控えの `hqHandle` を `ORCA terminal show --terminal <hqHandle> --json` で読む。live なら前の hq が動いているので、始めずに人に返す（hq を2つ動かさない。前の hq が応答しない（固まった）なら、人が前の hq のタブを閉じてから `/hq` を呼び直す）。無ければ `ORCA orchestration run-use --id <runId> --json` で前の Run をこの端末に結び直し、`node harness/scripts/hq-state.ts pending --all` で fleet の控えを読んでから、`check` の未処理（`question`・`escalation`・`worker_done`）を手順7のとおり処理する。控えで答え済み（`answer` がある）の質問には、人に聞かずに本文 `fleet のタブで人が答え済み` で返す（返し方は手順7）。`ORCA orchestration worker-list --run <runId> --json` の settle していない Dispatch ごとに `ORCA orchestration send --to dispatch:<Dispatch ID> --subject "hq-back" --body "hq が戻りました（session <短い ID>）" --json` で戻ったことを知らせ、控えの `hqHandle`・`hqSession`・`paneHandles`（手順6で作り直したもの）を自分のものにして `hq-state.ts ledger-save` で置く。
     - `run-use` が失敗した（Run が消えた・結べない）：手順4のとおり新しい Run を作り、fleet の控えの答えの無い質問を手順12の一覧に「fleet のタブ（テーマ）で答える」として出す（fleet は hq がいないときの退行のまま、人の答えを fleet のタブで受ける）。
     - 控えが無い（または `hqSession` が自分）：手順4の `worker-list` で聞き直して作り、`hq-state.ts ledger-save` で置く。
     - 控えの `fleets` に印 `"handover": true` の fleet（前の hq が「交代する」と返して、まだ起こし直していないもの）が残っていれば（#618）：`ORCA orchestration worker-list --run <runId> --json` でその `dispatch` を見る。settle していない（まだ動いている）なら、手順9の `worker_done` を待つ（受け取ったら手順7の「起こし直し」）。settle している・Dispatch が無い（Run が消えた・`dispatch` が無い）なら、手順7の「起こし直し」の 1〜5 を行う（1 の `worker-release` は、前の hq が解放していなければ行う）。起こせなかったら、印を残したまま手順12の一覧に「交代の途中の fleet（テーマ・Issue 番号）」として出す。
2. **hq は書き換えない**：hq はリポジトリのファイル（本体・fleet のワークスペース・Issue の worktree）を書き換えない。するのは、読むこと（`gh`・`node harness/scripts/agent.ts fleet-status`・`panes.ts`・`node harness/scripts/agent.ts usage`・Orca の読むコマンド）、指揮（Orca の orchestration と、待ちの見張り `node harness/scripts/hq-watch.ts` の実行）、引き継ぎの問いの判定と記録（手順8の `hq-takeover-ask.ts` の `check`・`record`）、fleet と hq 自身の端末への `/compact` の送信（手順7・8。`hq-compact.ts` と `hq-watch.ts` が送る）、起こした fleet に指示が入らなかったときの、fleet の端末への `ORCA terminal send` による Enter の1回だけの送信（手順4）、GitHub への記録（コメント・着手宣言）、intel への `SendMessage` と intel のタブの起こし方（本体での `ORCA terminal create`・`terminal send`。節「相談・アイデアを intel に回す」）だけ。Epic の Issue の作成と sub-issues への付け足しはしない（Epic の振り分けは App が行う。手順8）。リポジトリの中で書くのは印のファイルだけ（手順5の `.agent-harness-workspace`）。リポジトリの外の控え（scratchpad の一時ファイルと、スクリプトが git の共通ディレクトリの下に置く状態（段階のファイル・`hq-state.ts` の控え・`hq-heartbeat.json`・`hq-compact.ts` が書く `hq-compact.json`・`hq-takeover-ask.ts` が書く `hq-takeover-ask.json`））は書く（作業ツリーの外で、書き換えに数えない）。fleet も書き換えない（fleet の skill の「Orca の worker として動くとき」の4）。直接の進め方（節「ship を直接起こす進め方（`--direct`）」）のときだけ、ship の worker を起こすために `node harness/scripts/agent.ts claim`・`release`・`worktree`（Issue の worktree を作るだけで、中は書かない）と `node harness/scripts/accounts/probe.ts`・`pick.ts` も流す。コードや docs を書き換えるのは、Issue の worktree の中の ship だけ。
3. **テーマを決めて知らせる**：テーマは Epic（fleet のワークスペースは Epic ごとに1つ）。開いた Epic と子課題を `node harness/scripts/agent.ts fleet-status --json <子課題の番号>...` で読み、`hq-decide.ts themes`（手順8の空きの補充と同じ。`--fleet-status`・`--epic-children`・`--issues` に scratchpad のファイルを渡す）を流す。`judge` が `theme` なら、依存の鎖・`priority:*`・`area:*`・計画の `files` の重なりからの Epic と順番は判断の担当（hq-judge。節「判断の担当（hq-judge）」）が決める（人には聞かない）。候補が1つなら担当を呼ばずその Epic を起こす。テーマどうしで `files` が重なる組は、同時に起こさない。Epic に入っていない Issue をどう Epic にまとめるかは、hq が決めず聞かない。手順8の「Epic の振り分け」（App が行い、hq は一覧に出すだけ）に従う。決めたテーマ（Epic 番号・順番・選んだ理由を一言）は、手順12の一覧で人に知らせる。人が指示したテーマ（進めたい Epic・Issue の入力）と、人が止めるよう言ったテーマは、人の指示に従う（止めるよう言われたテーマは起こさない）。`--direct` の Epic は fleet を起こさず、節「ship を直接起こす進め方（`--direct`）」で進める。
4. **fleet の起動**：`ORCA status --json` で Orca を確かめ、`ORCA orchestration run-create --objective "<決めたテーマ>" --json` で Run を1つ作る（hq の Run。Run ID と hq の Claude の端末の handle を控えの `hq-fleets.json` に書き、`hq-state.ts ledger-save` で置く）。テーマごとに次で fleet を起こす。
   ```text
   ORCA orchestration worker-start --spec "<指示>" --worktree new-top-level --agent claude --display-name "fleet: #<Epic番号> <日本語の短い言葉>" --comment "Epic #<Epic番号>" --run <hq の Run ID> --json
   ```
   - 指示に入れるもの：fleet の skill の「Orca の worker として動くとき」に従うこと、`fleet-status` に渡す Issue 番号の集合、テーマの名前（ペインの `--label`。表示名の `fleet: ` の後ろ。Epic のタイトルから `type(scope): ` を除いたものと本文の Goal から、内容を表す日本語の短い言葉（目安 15 字まで。claude・Orca・mod などの固有名詞・コマンド名は英字のままでよく、`claude-mod` のような英語のスラッグにしない。例：`fleet: #520 claude の mod`）を一度だけ作り、同じ言葉を `--display-name`・`--label`・`.agent-harness-workspace`・控えのテーマの名前に使う。#591）、最初に自分のセッション ID（`AGENT_HARNESS_SESSION`）を `send`（件名 `session`）で hq に返すこと、heartbeat の本文に今の状況を一言入れること（Issue 番号・段階・次にすること・待っているもの。fleet の skill の「Orca の worker として動くとき」の 6）。名前は表示のためだけで、着手宣言・usage・`fleet-status` はセッション ID で見分ける。
   - 同時に動く fleet（`ORCA orchestration worker-list --run <hq の Run ID> --json` で settle していない Dispatch のうち、控えの `fleets` の Dispatch だけを数える。直接の進め方の ship の worker も hq の Run にいるため、控えの `ships` の Dispatch は数えない）は `hq.maxFleets` を超えない。fleet が ship を Orca の worker で動かすとき（fleet の skill の「Orca の worker で ship を動かすとき」）、ship の worker は fleet の Run にいるので、`--run` で絞れば数に入らない。上限に達していれば、次のテーマは起こさずに待ち、1つが片付いてから起こす。ship の数は手順8の空いた枠の割り当てで `hq.maxParallelShips` までにする。
   - 受け取りの `worker.stage` が `turn_start_unobserved` なら、終了コードによらず（0 以外でも）先にこの項目を行う（起動直後に送信の Enter が取りこぼされ、指示が入力欄に残る。#551）。`ORCA orchestration worker-read --dispatch <Dispatch ID> --limit 50 --json` を scratchpad のファイルに書き、`node harness/scripts/hq-state.ts start-failure-save --dispatch <Dispatch ID> --theme <テーマ> --stage turn_start_unobserved --screen-file <ファイル>` で画面を控える。`terminal.draft` が空でなければ、`ORCA terminal send --terminal <worker.agentTerminalHandle> --text "" --enter --wait-submit 30 --json` で Enter だけを1回送る（指示の文は送らない。同じ Dispatch に1回まで）。送った後にもう一度 `worker-read` を書き、`draft` が空なら `--resent accepted`、残っていれば `--resent unobserved` で控え直す。`draft` が空なら何も送らず `--resent none` で控える。Dispatch は作り直さない。`accepted` なら起動できたとみなし、下の「0 以外なら起こし直さない」の項目は飛ばして、次の「受け取ったら…`ledger-save`」に進む（片付けない。ワークスペースのパス・`startedAt` などが受け取りに無ければ `ORCA orchestration worker-show --dispatch <Dispatch ID> --json` から取る）。`unobserved`・`none` のときだけ下の項目に進み、手順12の一覧に画面の要点を出す。
   - `worker-start` が 0 以外で終わったら起こし直さない。受け取りの `failedStage`・`residualResources` を読み、`references/recovery-and-cleanup.md` に従う。
   - 受け取ったら、テーマ・Epic 番号・Dispatch ID・ワークスペースのパス・起こした時刻（`startedAt`）・Issue 番号の集合を控えの `hq-fleets.json` に書いて `hq-state.ts ledger-save` で置く。fleet から `session` が届いたら、そのセッション ID も書く。控えが無い・壊れた（`hq-state.ts ledger` が `null`）ときは、`ORCA orchestration worker-list --run <hq の Run ID> --json` で settle していない Dispatch ごとに `send` でセッション ID を聞き直して作り直す。テーマの名前（label）だけでセッションを引かない。
5. **印を置く**：fleet のワークスペースを作った直後に、Write で `<ワークスペースの絶対パス>/.agent-harness-workspace` を置く（中身はテーマの名前1行）。まだ印が無いので hook（`.claude/hooks/workspace-guard.ts`）に止められない。書き先は main の checkout の外（fleet のワークスペースの中）の絶対パスにする。印は `.gitignore` に入っているので、ワークスペースの `git status` に出ない。これ以降、ワークスペースの中の書き換えは hook が止める。
6. **ペイン**（#402）：hq が呼び出されたら（手順1の引き継ぎの後、fleet を起こす前に1回）、本体のワークスペースを次の並びで開く。左に hq の Claude（縦いっぱい）、真ん中の列に上から ① Epic/Issue → ② 人待ち → ③ ログ、右に intel の Claude。
   ```text
   ┌──────────────┬──────────────────────┬──────────────┐
   │              │ ① Epic/Issue         │              │
   │  hq の       ├──────────────────────┤  intel の    │
   │  Claude      │ ② 人待ち              │  Claude      │
   │              ├──────────────────────┤              │
   │              │ ③ ログ                │              │
   └──────────────┴──────────────────────┴──────────────┘
   ```
   - この手順の続きは [references/panes.md](references/panes.md)。ペインを作る・分け直す・閉じるときに読む。
7. **人の判断をまとめて聞く**：**ターンを終える前に見張りを置く**（置かないと、fleet の質問・`worker_done`・escalation が届いても hq のターンが始まらず、人に聞くことも次の fleet を起こすことも止まって全体が止まる。#559）。`node harness/scripts/hq-watch.ts --terminal <控えの hqHandle>` を Bash の run_in_background で置く（run_in_background の子プロセスから呼ぶので、Orca が呼び手を取り違えないよう hq 自身の端末の handle を明示する）。見張りは中で `ORCA orchestration check --wait --types "worker_done,escalation,question,status" --timeout-ms 900000 --json` を使い（heartbeat も待つ）、heartbeat だけの束は一言を `hq-heartbeat.json` に控えて ack し、hq は起こさない。見張りが終わると hq のターンが始まる：出力の `wake` が `messages` なら、束（question・escalation・worker_done・status。混ざった heartbeat は下の heartbeat の項のとおり）は、出力を scratchpad のファイルに書き、先に `node harness/scripts/hq-decide.ts route --wake <ファイル>` で振り分ける（条件を自分で読み分けない。結果の `items` の `action` に従って下のとおり処理する：`heartbeat-save`・`handover-check`・`ask-human`・`escalation`・`worker-done`・`tell-now`・`list`・`intel`・`notice-unmarked`）。`judge` が付いた item（`split`・`summary`）は、節「判断の担当（hq-judge）」のとおり担当を呼ぶ。処理したら、`node harness/scripts/hq-watch.ts --terminal <控えの hqHandle> --ack <delivery_id>` で ack と見張りの置き直しを1回で行う。`timeout` なら手順8へ進み、見張りを置き直す（見張りは `timeout` で戻る切れ目で、`hq.compactMinutes`（既定 180 分）以上経って hq の端末がターンを終えていれば hq 自身に `/compact` を送って縮め終わるのを待つ。出力に `compacted` があれば、`hq-state.ts ledger` を読み直してから手順8に進む。#737）。終了コード 1（標準エラーに理由）ならエラーを人に示して置き直し、続けて失敗するなら人に返す条件の「Orca のコマンドが動かない」にする。
   - この手順の続きは [references/asking.md](references/asking.md)。見張りが `messages` で返り、`route` の `items` を処理するときに読む。
8. **進んでいない fleet を見つける**：見張り（`hq-watch.ts`）が `timeout` で返るたび（15分ごと）に、`node harness/scripts/panes.ts fleets --session <今動いている fleet のセッション ID>...` を読む。`--session` なしで読まない（終わった・解放した・起こし直す前の fleet のスナップショットも OS の一時ディレクトリに残るため）。
   - この手順の続きは [references/sweep.md](references/sweep.md)。見張りが `timeout` で返るたびに読む。
9. **fleet が終わっても Epic は終わりではない**：`worker_done` は、控えの Dispatch（控えの `fleets` の Dispatch。`ships` のものは節「ship を直接起こす進め方（`--direct`）」の 5）と同じかを確かめてから受け取り、`--report-path` のファイルを読み、`judge` が `summary` なので担当（hq-judge）の `summary` で人に出す要点と人がすることの項目にまとめる（節「判断の担当（hq-judge）」）。fleet が人の Merge 待ちで返っても、終わったとみなさない。Epic が開いていれば（人の Merge 待ち・人の判断待ちが残る）、ワークスペースを残す（Epic の無い単発の fleet では、この条件を「`worker_done` を受け、集合の Issue が全部 Close した」と読む。人の判断待ちが残ればワークスペースを残す）。Epic が Close しても、その fleet の集合に Epic の外の Issue（hq が足したもの）があり `worker_done` がまだ届いていなければ、解放もワークスペースの削除もしない（`worker_done` を受けてから片付ける）。worker は `ORCA orchestration worker-release --dispatch <Dispatch ID> --json` で解放し、控えから外して `hq-state.ts ledger-save` で置く。Merge などで進められる子課題が出たら（`fleet-status` に「選ぶ」がある）、同じワークスペース（`--worktree path:<ワークスペースの絶対パス>`）に新しい fleet を起こす。新しい fleet はセッション ID が変わるので、前の fleet の宣言は手順10の引き継ぎの判定に従う。fleet が「今は進められない」（受け持ちが全部、時間を超えた人の判断待ち）で返ったら、その Epic には fleet を起こし直さず（脇に置いた Issue は「選ぶ」に出ない）、ワークスペースを残し、次の見回しを待たずに手順8の空きの補充で空いた枠を埋める（Epic に入っていない単発の Issue は #673）。人の判断が付いて「選ぶ」に戻ったら、同じワークスペースに起こす。
10. **止まった fleet の起こし直し**：
    - 起こし直すのは、`ORCA orchestration worker-list --include-remote --run <hq の Run ID> --json` の `projection.liveness` が `exited` のときだけ。`unverifiable`（absence を含む）は止まった証拠にしない（待ち続けるか、読んで確かめる）。
    - 同じ fleet（同じテーマ）は1時間に2回まで。起こし直したら Epic に hq の記録のコメント（先頭に目印 `<!-- agent-harness:hq-restart theme=<Epic番号> -->`、本文に時刻・前と新しいセッションの短い ID・理由 `exited`）を残し、回数は同じ目印のコメントの直近1時間の件数で数える（hq の `/clear`・交代でも数え直しにならない）。超えたら起こし直さず、人に知らせる。
    - 起こし直す前に、その fleet の Issue 番号を渡した `fleet-status --json` をファイルに書き、`node harness/scripts/hq-decide.ts takeover --theme <テーマ> --fleet-status <file>` を流して結果に従う（宣言のセッションと控えを自分で見比べない。控えは `ledger-save` を置き直す前のものを読む）。`decision` が `auto`（宣言がすべて hq が自分で起こした fleet のセッション＝控えの今の fleet と `priorSessions` のもの。`priorSessions` は控えに入れてから `staleHours` 以内のもの。過ぎたものは `unknown` になり聞く）なら人に聞かず、`ask` なら `unknown` の宣言だけ「前の fleet の宣言 #…（N 件）を新しい fleet に引き継ぐか」を AskUserQuestion で1問だけ聞き（1件ずつ聞かない。引き継ぎは人が決める）、`known` の分は聞かずに引き継ぐ。`none` は引き継ぐものが無いので聞かない。`fleet.shipMode` が `worker` のときの ship のセッション（fleet と別の ID）の宣言は控えに無いので `unknown` になり、聞く。
    - 引き継ぐもの（`auto` の分・`known` の分・人が引き継ぐと答えた分）は、新しい fleet の指示に聞かずに引き継ぐ分は「hq の判定：前の fleet（hq が起こしたもの）の宣言を引き継ぐ」、人が答えた分は「人の決定：前の宣言を引き継ぐ」と、Issue の段階は `node harness/scripts/agent.ts claim <番号> --manual --stage <段階> --takeover`、PR の段階は `node harness/scripts/agent.ts claim <PR番号> --manual --stage judge|fix|sync --takeover` で出し直すことを書く。fleet が `ask` で引き継ぎを聞いてきたら、hq の判定（または人の同じ答え）を `reply` で返し、人に聞き直さない。聞かずに引き継いだ宣言は、Epic（単発の fleet は各 Issue）に `post-judgment`（`stage` は `other`、`basis` は `recorded`。当たった規則は「hq が自分で起こした fleet のセッションの引き継ぎは人に上げる場面から除く」）で残し、手順12の一覧の「決めたこと（覆すなら）」に出す。引き継がないなら、その Issue を指示から外し、手順12の一覧に書く。
    - 止め方と新しい Dispatch（`worker-stop`・`worker-abandon`、`worker-start --task <task_id> --retry-of <dispatch_id>`、同じワークスペース）は `references/recovery-and-cleanup.md` に従う。起こし直したら、控えのその fleet の `session`（新しい fleet から届くまで null）・`startedAt`・`dispatch` を新しい fleet のものに書き換えて `hq-state.ts ledger-save` で置く（手順6のペインは控えを読み直して追うので、作り直さない）。
11. **片付け**：Epic が Close した（`gh issue view <Epic番号> --json state` が `CLOSED`）テーマだけを片付ける（Epic の外の Issue が集合にあって `worker_done` がまだなら待つ。Epic の無い単発の fleet は `worker_done` を受け、集合の Issue が全部 Close したら片付ける）。fleet の worker を `worker-release` で解放し、控えから外して `hq-state.ts ledger-save` で置き（手順6のペインは控えを読み直して追うので、作り直さない）、`ORCA worktree rm --worktree path:<ワークスペースの絶対パス> --json` でワークスペースを消す。人の判断待ちだけが残るとき（Epic が開いている）は残す。印 `handover` の残る fleet を控えから外すときは、`ledger-save` に `--release-handover <テーマ>` を付ける（付けないと前の控えから残される。#618）。片付けたら、次の見回しを待たずに手順8の空きの補充を行う。
12. **人がすることの一覧**：各 fleet の `worker_done` のレポート（担当の `summary` の要点と人がすることの項目）と `node harness/scripts/panes.ts hq todo --once` の一覧を1つにまとめて人に出す（起こしたテーマ（手順3で hq が決めた Epic と順番・理由の一言）・テーマごとの今の状況（手順7で控えた heartbeat の一言と受けた時刻。一言なしならそう書く）・Merge・見届け待ち（Merge 済み・Merge されずに閉じた PR）・例外ラベル・`setup.ts` の要否・Merge 後の確かめ・人の判断待ち・脇に置いた人の判断待ち（Issue・止まっている時間・決めてほしいこと。fleet のレポートから1行ずつ。前の一覧と同じものは聞き直さない）・進んでいない fleet・起こし直しの上限を超えた fleet・交代した fleet（テーマ・前と新しいワークスペース、古いワークスペースを消せなかったときはその理由）・決めたこと（覆すなら）（手順10で `hq-decide.ts takeover` の判定により聞かずに引き継いだ宣言。#番号・段階・前の session の短い ID）・引き継がなかった宣言（手順10の起こし直しで人が引き継がないと決めた前の fleet の宣言。期限切れの着手宣言と同じ宣言は「期限切れの着手宣言」に1回だけ出し、ここに重ねない）・手順7でためた fleet の報告・連絡（自動 Merge の `ready-<PR>`・`merged`・`verdict`・`wait`・intel に回せなかった `notice`）・返せなくなった答え・intel に回せなかった気づき（節「相談・アイデアを intel に回す」）・起動の失敗（`node harness/scripts/hq-state.ts start-failures`）・空きの補充で起こした fleet（テーマ・選んだ理由）・起こせる Epic なし（理由）・空いた枠の割り当て（どの Issue をどの fleet に渡したか・起こした fleet・空き待ちと、`assign` の `running`／`hq.maxParallelShips`）・直接の Epic ごとの ship（Issue・段階・heartbeat の一言と、`worker_done` のレポートの項目。節「ship を直接起こす進め方（`--direct`）」））。手順8の止まったタスクの見回しからは、割り振ったもの（どの fleet に渡したか）・聞いたもの（引き継ぎの問い。止まった宣言は「期限切れの着手宣言」の行に答えを添え、重ねて出さない）・期限切れの着手宣言（#番号・段階・session の短い ID。`stale` が真の控えに無い宣言。引き継ぎの問いへの答えもこの行に添える。見つけたもの全部を毎回出す）・ためている引き継ぎの問い（N 件。次に聞く時刻 `nextAskAt`。見送ったまま状況の変わらないものの数 `skippedDeclined`）・長く出力の無いタブ（手順8の `panes.ts idle` の行。閉じない）・ほかのセッションが着手中（#番号・段階・session の短い ID。`stale` が偽の控えに無い宣言）・Epic に入っていない Issue（ダッシュボードの節の行。Jev の一番高い Epic と確率か「未判定」）・人が決めなかったもの（答え無し・拒まれた・空き待ち）と、patrol の未採用の下書きの数を足す。費用は手順8の `panes.ts fleets --session` の各行の `totalUsd` と、hq 自身の `node harness/scripts/agent.ts usage` をまとめる。
   - **Merge 待ちの PR の状態を確かめる**（#724）：一覧を出す前に、「Merge」に載せる PR 番号（手順7で受けた `ready-<PR>`、`worker_done` のレポート、`panes.ts hq todo --once` の Merge 待ち）を集めて重複を1つにまとめ、`gh api graphql` を1回だけ使って状態を読む（PR が1件も無ければ読まない）。`repository(owner:, name:)` の下に別名 `p<番号>: pullRequest(number: <番号>) { number state mergedAt closingIssuesReferences(first: 5) { nodes { number state } } }` を PR ごとに並べる。人が Merge した後に fleet が終わると `merged-<PR>` が届かず、Merge 済みの PR が一覧に残るため（手順7の見張りとは別の、一覧を出すときの1回の確かめ）。
     - `state` が `MERGED`：「Merge」から外す。`merged-<PR>` を受けていれば、手順7でためた報告として出し、見届け待ちには出さない。受けていなければ、`closingIssuesReferences` の Issue が控え（`hq-fleets.json`）の `fleets[].issues` に入っているか（受け持つ fleet が生きているか）で分ける。入っていれば、その fleet に任せる（fleet が `fleet-status` の「次にやること」で `merged` の段階を ship に渡す。hq は何も送らない）と一言書く。入っていなければ（`worker_done` の後に控えから外れた fleet を含む）、「見届け待ち（Merge 済み）」に `PR #番号（#Issue、Issue の state）` を出す（Issue が `CLOSED` なら「Close 済み」と添える）。
     - `state` が `CLOSED`（Merge されずに閉じた）：「Merge」から外し、「見届け待ち」に「Merge されずに閉じた PR #番号」と出す。
     - 読み取りが失敗したとき（`gh` のエラー）：外さずに出し、「PR の状態を確かめられなかった（理由）」と一覧に書く。止まらない。
     - 手順7で Human Merge の `ready-<PR>` を人にすぐ伝えるのは Merge 前の知らせで、この確かめとは別に行う。
