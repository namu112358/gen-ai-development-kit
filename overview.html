ハーネスの全体図

GitHub の Issue を起点に、Claude（AI）が計画・実装・判定を進め、専用の GitHub App が各段階の関所（ゲート）を受け持つ仕組みです。危なくない小さな変更（Risk が low）は人の手を借りずに Merge まで進み、それ以外は人が確かめて Merge します。

流れ：Issue から Merge まで

人は Issue を書いて「着手してよい」の印を付けるだけで、あとは次の順に進みます。人が付き添う Claude のセッションに「#番号 を ship して」と頼むと、この流れを人の Merge 待ちか人の判断待ちまで進めます。

  1. 1

    Issue

    人

    「Agent タスク」の Issue Form で、目的（Goal）・要件・受け入れ条件（AC）を書き、agent:ready を付けます。App が本文の書式を確かめます。

  2. 2

    計画

    ClaudeApp

    Claude が実装方針と「触るファイル一覧」・想定 Risk を計画コメントに書きます（投稿前に plan-critic が批評）。App の計画ゲートが中身を機械的に検査し、通れば agent:plan-ok を付けます。

    人に返る分かれ道：人の判断が要る、AC を変える提案がある、未解決の質問がある、Risk が high 以上、触るファイル一覧が無い、ガードレールに触れる、のどれかなら agent:plan-review で止まり、人が「進める／直す／やめる」を決めます。
  3. 3

    実装

    Claude

    Claude が claude/ ブランチで実装し、テストを通して、Closes #番号 付きの Draft PR（作業中の PR）を出します。App は変更ファイルが計画の一覧に収まるか（範囲照合）と、テストを甘くしていないか（agent/tests）を見ます。

  4. 4

    判定

    ClaudeAppJev

    Reviewer（AC を満たすか）と Risk Agent（壊れたときの影響を8問で）が判定し、判定コメントを投稿します。App が受け付けてチェック（agent/review・agent/risk）に変え、合格なら PR を Ready にします。Jev もいまは記録のために同じ8問に答えます。

    直すループ：ブロッキング指摘（直すまで Merge させない指摘）があれば Claude が直して判定し直します。上限を超えると agent:blocked で人に返ります。
  5. 5

    Merge

    App人

    判定の結果で、自動 Merge か Human Merge（人が Merge）に分かれます（下の図）。

誰が何をするか

4者で役割を分けています。Claude は人と同じ GitHub 名義で動くので、名義では区別しません。信頼できる印は App が付けたものだけです。

人

  • Issue を書き、agent:ready を付ける
  • 計画ゲートで止まった Issue の進め方を決める
  • Human Merge の PR を確かめて Merge する
  • 止める：agent:hold・停止スイッチ
  • 例外ラベル（test:exempt など）を付けるかを決める

Claude（付き添いのセッション）

  • 計画を書く（plan-critic が批評）
  • テストを書き（test-designer）、実装して Draft PR を出す
  • 判定する（Reviewer・Risk Agent）
  • 指摘を直す、main を取り込む

しないこと：Merge、Draft の解除、main への push、保護ラベルの付け外し（見張りの hook が止める）

App（専用 GitHub App）

  • 計画ゲート（agent:plan-ok を付けられるのは App だけ）
  • 判定の受け付け、Ready 化、auto-merge を付ける
  • 必須チェック（merge-route・agent/tests・agent/plan-link など）
  • 足りないラベルを付け、ダッシュボードに一覧を出す

GitHub Actions の数秒のジョブで動く。Claude は動かさず、PR のコードも実行しない

Jev（TypeSafe AI の判定モデル）

  • Risk の8問に確率付きで答える。いまは Claude の判定と並べて記録するだけ（シャドー判定）
  • Issue の種類・領域・優先度を提案し、確かなときは足りない priority:*・area:* を付ける材料になる

外れがないと確かめてから、Risk 判定を任せる予定

ディレクトリの地図

各ディレクトリの README.md に、中のファイルを1行ずつ説明しています。ガードレール は、変えると必ず人が Merge する場所です（Agent が自分を縛る仕組み）。

harness/ 本体

  • gates/ App として動くゲート ガードレール
  • lib/ 判断のロジック（書式・範囲照合・merge-route など） ガードレール
  • scripts/ 手元で動かすコマンド（agent.ts・setup.ts など）
  • templates/ 導入先に写す設定の見本 ガードレール
  • CLAUDE.harness.md ハーネスの規則（CLAUDE.md が読み込む） ガードレール
  • managed.json 導入先に配るファイルの一覧
  • test/ テスト（npm run check）

.claude/ Claude への指示

  • skills/ 付き添いのセッションの手順（ship・plan・implement・judge・fix・sync・fleet・review-panel・qa-retro）。fleet は入れ子にできる環境なら Issue ごとに ship をサブエージェントで並行に動かし、できなければ段階を交互に進める
  • agents/ サブエージェント（Reviewer・Risk Agent・plan-critic・test-designer・合体版のレビューの担当（review-*））
  • hooks/ 見張りの hook ガードレール
  • settings.json させない操作の一覧 ガードレール
  • routine.md 定期 Routine の手順（将来の構想）

.github/ GitHub の設定 ガードレール

  • ISSUE_TEMPLATE/ Issue Form（「Agent タスク」）
  • pull_request_template.md PR 本文の見本
  • workflows/ CI（ci.yml）とゲート（gate.yml）

docs/ 説明書

  • operations.md 運用・ラベル・止める仕組み
  • risk-policy.md 自動 Merge の8問と条件
  • glossary.md 用語集
  • setup.md 導入手順 ほか

root の主なファイル

  • README.md 入口の説明
  • CLAUDE.md このリポジトリの約束ごと（ハーネスの規則は harness/CLAUDE.harness.md から読み込む） ガードレール
  • harness.config.json 導入先ごとの設定（ガードレールの一覧など） ガードレール
  • overview.html このページ

ラベルの意味

主なものです。すべての一覧と細かい決まりは docs/operations.md の「ラベル」にあります。

ラベル付ける者意味
agent:ready人着手してよい
agent:plan-okApp のみ計画ゲートを通った。実装に進める
agent:plan-reviewClaude / App計画に人の判断が要る。人が付き添うセッションで進める
agent:waitingClaude / Appほかの Issue の完了待ち（終わると App が外す）
agent:blockedClaude / App / 人人の対応が必要。理由をコメントに残す
agent:hold人この Issue・PR だけ止める
agent:auto-merge-stopped人 / App停止スイッチ。ダッシュボードに付くと自動 Merge が全部止まる（自動 Merge した PR が revert されると App が付ける）
agent:delegate-merge人のみ委任 Merge。ダッシュボードに付けると期限つきで Merge を App に委ね、ガードレール・Risk が理由の PR も自動 Merge する。外す・期限切れ（定期実行が外す）・停止スイッチで、委任で付けた auto-merge を外す
risk:*Claude / App壊れたときの影響の大きさ（low・medium・high・critical）
priority:*人 / App / Claude優先度（highest〜lowest の5段階）。高いものから進める
type:*人 / App課題の種類（feat・fix・docs など。タイトルと同じ）
area:*App / Claude変更の領域（harness・docs など）
size:*AppPR の差分の行数（XS〜XXL）
epicApp子課題に分けた親 Issue
review:exempt
plan:exempt
test:exempt		人例外として必須チェックを通す（付けた時点の差分にだけ効く。plan:exempt は紐付けの例外）
